Sobre o projeto

Uma plataforma de playlists, sem servidor

O ITransferMusic é uma plataforma web para transferir, gerar e sincronizar playlists entre serviços de streaming, com backend FastAPI + MongoDB e frontend Angular. Esta versão publicada é uma demo estática: o frontend fala com a mesma API, mas quem responde é uma cópia dela rodando no seu navegador.

Como a demo espelha a API

O app chama exatamente as rotas de BackEnd/src/api/v1 (base http://localhost:8000/api/v1, a mesma do frontend original), com os mesmos DTOs e as mesmas mensagens de erro, inclusive o formato 422 do Pydantic. No build da demo, um interceptor do HttpClient responde essas chamadas com uma tradução dos services Python e grava no localStorage.

Diferenças assumidas

Ao espelhar a API apareceram alguns bugs reais do original. Eles foram corrigidos só na demo (o backend continua intacto) e estão comentados no código.

  1. 01 · agendador

    Uma sincronização marcada entre 23:46 e 23:59 UTC nunca rodava: o _is_due monta o horário agendado no dia de hoje, e no disparo das 00:00 ele cai no futuro. A demo usa a última ocorrência antes do disparo.

  2. 02 · transferência

    Quando nenhuma faixa era encontrada (ou a origem estava vazia), o original criava mesmo assim uma playlist vazia no destino e marcava a transferência como falha. A demo não cria nada.

  3. 03 · gerador

    Ao salvar uma playlist gerada, o original gravava matched=true em todas as faixas, até nas que não achou no destino. A demo grava o resultado real.

  4. 04 · contas

    O POST /transfers aceitava o job mesmo sem a conta de origem ou destino vinculada e ele falhava depois, em segundo plano. A demo recusa na hora com 400 e a mesma mensagem.

  5. 05 · sincronização

    O POST /syncs/{id}/run respondia 202 mesmo para uma sincronização que não existe. A demo responde 404. O PATCH também passa a atualizar updated_at.

  6. 06 · limite

    O GET /transfers aceitava qualquer limit. A demo limita entre 1 e 100.

  7. 07 · extensões

    Rotas que só a demo tem: POST /transfers/preview (o matching sem rodar o job, para a pré-visualização) e GET /__demo/scheduler (o job do APScheduler). Cada resultado ganha confidence e matched_name. Com o backend real, a pré-visualização avisa que não existe.

  8. 08 · provedores

    No original só Spotify e YouTube Music têm OAuth de verdade (Apple Music e Amazon Music são stubs, Deezer está fora de escopo). A demo simula os cinco, com uma tela de autorização que diz que é simulada.

Perguntas frequentes

Como funciona a transferência?

Você escolhe a origem, o destino e as playlists (ou faixas). O backend lê cada faixa, busca título e artista no destino e cria uma playlist nova com tudo o que encontrou. O trabalho roda em segundo plano: pode fechar a página e voltar depois.

O que acontece com as faixas que não são encontradas?

A correspondência é por busca textual. Faixas fora do catálogo do destino, de outra região ou com metadados diferentes podem não aparecer. A transferência vira parcial (por exemplo, 42 de 50) e a lista completa fica no histórico.

Meus dados estão seguros?

No app real, só OAuth oficial: a senha dos serviços nunca passa pelo ITransferMusic e os tokens são cifrados com Fernet antes de ir para o banco. Nesta demo não existe conta real nenhuma: nada é enviado a provedor algum e os dados ficam no localStorage.

As playlists ficam sincronizadas sozinhas?

Só se você criar uma sincronização. Ela liga a playlist de origem à cópia no destino; o agendador roda a cada 15 minutos e, no horário escolhido (diário ou semanal), copia as faixas novas. O modo espelho também remove faixas, quando os dois lados são do mesmo serviço.

E se eu apagar a playlist no destino?

O endpoint /alive detecta que ela sumiu: o histórico mantém o registro com todas as faixas e avisa que a playlist foi removida do provedor.

Posso ver o código?

Sim: o repositório tem o backend FastAPI original e este frontend. O README explica como rodar o full stack com MongoDB e credenciais OAuth próprias.
